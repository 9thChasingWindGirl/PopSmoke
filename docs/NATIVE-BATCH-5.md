# 原生第五批：Supabase 记录双向同步（队列驱动）

这一批补的是第四批明确留下的缺口：**记录本身的双向同步**。
第四批只做了 Supabase 的账号与 `app_settings`（配置），`smoke_logs` 一条都没动。

## 两条通道的职责（本批确定，不再混用）

| | Supabase | 飞书 |
|---|---|---|
| 方向 | **双向**（推 + 拉） | **单向**（本地 → 远端备份） |
| 内容 | 账号、`app_settings`、`smoke_logs` | 记录备份 |
| 触发 | 用户点同步 / 入队后手动推 | 用户点"备份""恢复" |
| 冲突 | 按队列判定谁新 | 不判定，按 id 合并 |

一句话：**飞书是备份目的地，Supabase 是能来回同步的另一份数据。**

## 队列：为什么必须有

手机最常见的两个场景——地铁里信号断、以及连点三下记录——直接写云端都会变成三次失败弹窗。
队列把"记录"和"上传"解耦：记录永远瞬时成功，上传什么时候成功由网络决定。

实现：`data/sync/SyncQueue.kt`

- `SyncOp(type, userId, logId, timestamp, recordIndex, status, attempts)` —— 每条操作自带快照，
  推送时不再回查本地（回查会遇到"记录已经删了"只能猜）。
- 落盘在 `sync-queue.json`，**不进 `StoreState`**：它不是用户数据，备份/恢复时不该被带走。
- 先写 `.tmp` 再改名：落盘中途被杀掉时保留旧队列，不留一个截断的 JSON。
- 队列项带 `userId`：换账号登录时，上一个人的积压不能被推给新账号（真会发生，不是理论问题）。

### 合并规则（这段是重点）

| 已有 | 新操作 | 结果 |
|---|---|---|
| Create | Update | 保留一条 Create，快照换成最新值 |
| Update | Update | 只留最后一条（前一次的值永远不会被谁看到） |
| 任意 | Delete | 清掉同 id 的所有操作，只留 Delete |
| 任意 | Create | 清掉同 id 的旧操作，只留 Create |

没有这层合并，改两次时间就会推两条 update，先改后删还会推一条"已经删掉的记录"。

### 推送

`LogSyncService.pushPending()`：从队首逐条推，成功出队，**第一条失败就停**。

失败即停而不是继续：断网之后每一条都会失败，继续跑只会把整个队列标成 FAILED，
用户反而看不出是哪条先出的问题。失败的那条保留 `status=Failed`，界面可以单条重试。

返回策略：一条都没成功才报错给界面；部分成功就报数字（`上传 3 · 失败 1`）。

跳过的情形：Create/Update 对应的记录在本地已不存在（清空数据后残留的队列项）→ 直接出队，不发请求。
Delete 不检查存在性，因为它本来就指向一条已经不存在的记录。

### 拉取

`pullMerge()` → `LogRepository.applyRemote(remote, skipIds)`，三条规则：

1. 云端有、本地无 → 新增
2. 两边都有且时间不同 → **只有该 id 不在队列里时**才用云端值覆盖
3. `skipIds`（队列里有 pending 的 id）一律不动

第 2 条是这套设计的核心：队列在这里充当"本地有未提交修改"的唯一标记，
不需要再维护一张脏标记表。没有它，另一台设备的旧值会把用户刚调的时间悄悄盖掉。

`syncAll()` = 先推后拉。顺序不能反：先拉会把云端旧值盖在本地未推送的修改上
（新增记录会先被拉进来占位）。

## 三个实现细节

**1. 上传用 `POST ?on_conflict=id` 而不是 insert。**
队列重试会把同一条记录再发一次，insert 撞主键返回 409，会把"网络抖了一下"
变成"这条永远同步不上去"。`Prefer: resolution=merge-duplicates` 让重发幂等。

**2. 拉取要翻页。**
PostgREST 单次最多 1000 行，多出来的**静默截断**。用户看到"云端 1000 条"而本地记了 1200 支，
只会以为数据丢了。`fetchCloudLogs` 循环拉到不足一页，上限 20000 条。

**3. 合并后必须按天重算序号。**
远端自报的 `record_index` 是它那台设备当天数出来的。手机记 3 支、平板记 2 支，
合并后那天有 5 支，沿用旧编号会出现两个 #3、缺 #4。统一交给 `reindexByDay`。

## 界面

- **分析页**：新增"同步队列"终端卡（黑头 + 全部同步/清空 + 每行状态与单条动作 + 灰状态栏），
  位置在操作日志**之前** —— 队列是"还欠什么"需要动作，日志是"发生过什么"只需查阅。
- **分析页顶部"云同步"按钮**：第四批它只会跳到设置页，用户点完以为同步过了。
  现在已登录就真的同步（按钮上带待推条数），未登录才做引导。
- **设置页账户卡**：登录态新增"同步队列 / 立即同步"一行，与"上传设置、从云端恢复"分开 ——
  两者走不同接口，混在一起会让人以为点一次全同步了。

队列卡有两处刻意与 Web 不同：
1. 每行拆成两排（时间+内容 / 状态+动作）。手机宽度下把五个元素挤一行，消息会被压成两三个字。
2. 状态徽标用 12sp 而不是 10sp：10sp 的中文会糊成一片，"待同步"看着像"诗同步"。
3. 空态按内容撑开、不显示状态栏，与 Web 的 `p-4` 空态一致；一块 192dp 的空白面板
   会让人以为列表没加载出来。

## 已知限制（写清楚比藏着好）

1. **远端删除不传播**。`smoke_logs` 没有墓碑列，远端少一条无法区分"另一台设备删了"
   和"本地新增还没上传"，按缺失删本地会误删新记录。
2. **清空本地不会清云端**。与 Web 一致：清空是本地操作，队列里这些记录的待推项会被丢掉，
   否则"清完又从云端回来"。要清云端需另做"删除云端数据"。
3. **没有自动/后台同步**。Web 的 `autoSyncEnabled` 默认也是关闭。
   真要自动推，应该配 WorkManager + 指数退避，否则弱网下会堆一串失败请求。
4. **一次拉全量**。单账号上千条时每次同步都要翻几页。真要优化应该按 `updated_at` 水位做增量，
   但那需要表上有 `updated_at` 且写入时维护它。

## 首次上手建议顺序

1. 接口页填 Supabase URL + anon key
2. 设置页注册账号（若项目开了邮箱验证，会提示"邮件已发"）
3. 记两支烟 → 分析页底部队列应出现 2 条待同步
4. 点"全部同步" → 队列清空；另一台设备登录 → 点立即同步，记录应出现且序号连续
5. 断网后记一支 → 队列出现且点同步会报网络错误（这是预期），恢复网络后点该条的"同步"
