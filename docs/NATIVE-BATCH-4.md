# 原生第四批：账户与云同步

前三批把界面和本地功能补齐了，这一批接的是"换手机之后数据还在不在"。按你的说明，两条通道各干各的事，没有合并成一个开关：

| 通道 | 职责 | 具体表 / 端点 |
|------|------|---------------|
| **Supabase** | 账户 + 配置（每日上限、阈值、主题、语言） | GoTrue `/auth/v1/*`、PostgREST `app_settings` |
| **飞书** | 记录备份（一条烟 = 一条记录） | 自建中继 `GET/POST {url}` → 多维表格 |

这么分的原因：跨设备最痛的不是"少了几条记录"，而是"上限被重置成 10、主题回到橙色"——App 突然不是自己的了。反过来，记录量会一直长，放到飞书那张用户本来就在维护的表里更合适。

## 1. 账户（Supabase）

- 邮箱 + 密码登录 / 注册 / 登出，入口在设置页顶部一张卡。
- 三种状态而不是一个开关：没配地址 → 只给"去接口页"；已配置未登录 → 邮箱/密码表单；已登录 → 邮箱 + 上传/恢复/登出。避免"输完密码才发现根本没配 Supabase"。
- 注册时项目若开了邮箱验证，接口只返回 user 不返回 token。这种情况显示"验证邮件已发送"，**不假装登录成功**。
- 令牌持久化：`access_token` + `refresh_token` + 绝对过期时间，用 Keystore AES-GCM 加密写 `pop-data/session.enc`（复用第二批的 `SecureStore`）。refresh_token 等同于密码，不能明文放 SharedPreferences。
- 冷启动 `restore()`：令牌还新鲜直接用；过期了就刷一次；刷不动（被吊销 / 改过密码）才清本地会话。
- 任何需要鉴权的请求都走 `authorized {}`：先确保令牌新鲜，遇到 401 刷新后**重试一次**。用户不该因为"令牌恰好在这分钟过期"被要求重新登录。

## 2. 配置同步与冲突

`app_settings` 一行：`daily_limit / warning_limit / theme_color / language`（老的 camelCase 也认，Web 端做过同样的兼容）。

写入用 **PATCH 再按需 POST**：PATCH 是幂等的，行不存在返回空数组，再 POST 插入。不用 `POST + on_conflict=user_id` —— 表里若还有自增主键 `id`，把冲突目标换成 user_id 会要求那一列有唯一约束，配错直接 500。

**登录后不自动覆盖**。逻辑是：
1. 云端没有这一行 → 把本地上传（首次登录，答案唯一）
2. 云端有且与本地一致 → 什么都不做
3. 云端有但不同 → 弹窗列出行数差异，用户选"使用云端"或"保留本地"

第 3 种必须问：在新手机上先调了主题、或者想拿回旧配置，从数据上看一模一样。关掉弹窗（点遮罩/返回键）不执行任何同步，下次登录还会再问。

## 3. 飞书备份

- 备份：先 `GET` 一遍远端记录，得到 id 集合，只 `POST` 本地缺的那些。
  - 判断依据是**远端自己的 id**，而不是本地记一份"已备份清单"：清单会因清数据、换设备、手动改表而失真，远端永远准。代价是每次多一个 GET，换来"不会重复写入"。
- 恢复：`GET` 全量 → 按 id 合并进本地 → 按天重算"当天第几支"。
  - 必须重算：远端 idx 是那台设备当天数出来的。手机记 3 支、平板记 2 支，合并后那天有 5 支；沿用旧编号会出现两个 #3、缺 #4。
- 远端记录允许缺 `timestamp`（手填表格常见），用 `record_date + record_time` 反推；反推失败就丢掉这条，不造 1970 年的记录。
- 部分成功会照样报数字：`上传 47 · 已存在 120 · 失败 3`。只说"成功"等于让用户下次再点一遍确认。

## 4. 网络层

没有引入 OkHttp / Ktor：这一批只有 8 个端点、请求体全是 JSON、没有上传下载。`HttpURLConnection` + `org.json` 就够，APK 只涨了 0.1MB（8.0 → 8.1MB）。

- `HttpTransport` 是接口，测试里换成 Fake，能断言"发了什么请求、什么顺序、带没带令牌"。
- 超时 12s 连接 / 15s 读取。
- 失败归成 13 种 `CloudIssue`，界面翻译成四语言；服务端英文原文只在 `detail` 里留着，不直接糊到屏幕上。

## 5. 验证

- **12 条 `CloudServiceTest`**：登录请求形态、密码错映射、短密码不发请求、注册需验证、过期令牌先刷、401 重试一次、刷新失败清会话、PATCH 成功不再 POST、PATCH 空数组转 POST、备份只传缺失、飞书 `code≠0` 映射、未配置不发请求。
- **1 条仓库测试**：合并远端后序号重排为 1/2/3，且重复合并是幂等的。
- **19 张截图**（新增 `settings_account_signed_in_zh`、`settings_account_signed_out_zh`、`settings_cloud_conflict_zh`），`verifyPaparazziDebug` 通过。
- 文案 465 键 × 4 语言，`gen-strings --check` 一致；令牌 `--check` 一致。

## 6. 与 Web 版的差异（有意为之）

| 点 | Web | 原生 | 原因 |
|----|-----|------|------|
| 登录入口 | 整页弹窗 + 找回密码流程 | 设置页一张卡 | 手机上登录是低频动作，占满一屏不值得 |
| 密码处理 | 配置加密 + 用户记密码 | 不落盘，仅内存 | Keystore 已经解决了"密钥怎么存"，不需要用户再记一个 |
| 同步时机 | 记录时逐条打云 | 手动触发 | 一次点按就发网络请求，弱网下会让"记录"这个核心动作变慢 |
| 失败提示 | 服务端原文 | 归一化 + 四语言 | 英文 SQL 报错对用户没有意义 |

## 7. 仍未做

- **头像**：Web 用 `avatars` 桶，原生没做图片选择 + 裁剪 + 上传，账号卡只显示邮箱。
- **找回密码**：需要邮件深链回 App（`intent-filter` + `access_token` 片段解析），是独立一条链路。
- **自动同步**：登录后不会定时/记录时后台推送，只在用户点按钮时同步。真要做建议用 WorkManager + 指数退避，否则弱网下会堆积失败请求。
